# 견적서 웹 뷰어 MVP PRD 생성 프롬프트

> 사용법: 이 파일 내용을 Claude Code에 그대로 붙여넣거나 `@docs/PRD_PROMPT.md 대로 PRD 작성해줘`라고 요청한다.
> 결과물은 `docs/PRD.md`에 생성된다.

---

## 역할

너는 B2B SaaS 경험이 많은 시니어 PM이자 Spring 백엔드 테크 리드야.
개발자가 이 문서만 보고 바로 첫 마일스톤 구현에 들어갈 수 있는 **MVP PRD**를 작성해.

## 제품 한 줄 정의

운영자가 **Notion 데이터베이스**에 입력한 견적서를, 클라이언트가 **공유 링크로 웹에서 확인**하고 **PDF로 다운로드**할 수 있는 웹 서비스.

---

## 1단계: 사전 조사 (PRD 작성 전에 반드시 수행)

### 1-1. 레포 규칙 파악

아래 파일을 먼저 읽고, PRD의 기술 설계가 이 규칙과 어긋나지 않게 해.

- `CLAUDE.md` — 아키텍처 규칙, 버전 관리 정책, 스택 특유의 함정, 의도적으로 빠진 것
- `build.gradle.kts`, `gradle/libs.versions.toml` — 현재 의존성
- `src/main/java/com/example/starterkit/domain/user/` — 새 도메인이 복제할 기준 구조
- `src/main/java/com/example/starterkit/global/` — `ApiResponse`, `ErrorCode`, `BusinessException`, `GlobalExceptionHandler`

PRD에 반드시 반영할 규칙:

| 규칙 | PRD에 반영할 내용 |
|---|---|
| 레이어드 아키텍처 (`global/` + `domain/<도메인>/`) | 새 도메인 패키지 구성(예: `domain/quote`)과 레이어별 책임 |
| 트랜잭션 경계는 Service에만 | DB를 쓰는 경우 트랜잭션 범위 명시 |
| 모든 응답은 `ApiResponse<T>` | API 명세의 응답 예시를 `{ success, data, error }` 형태로 작성 |
| 새 오류는 `ErrorCode` enum에 추가 | 예외 시나리오마다 `ErrorCode` 이름, HTTP 상태, 메시지 정의 |
| DTO는 record, MapStruct는 엔티티 → 응답 DTO 단방향 | Notion 응답 → 도메인 모델 → 응답 DTO 변환 경로 정의 |
| 스키마 변경은 Flyway 전용 (`ddl-auto: validate`) | 로컬 DB에 저장하는 데이터가 있으면 `V{n}__{설명}.sql` 목록 명시 |
| OSIV 꺼짐 | Controller에는 DTO만 전달 |

### 1-2. "의도적으로 빠진 것" 처리

`CLAUDE.md`에 유보 항목으로 적힌 것(Spring Security, QueryDSL, Spotless/Checkstyle)은 **PRD에서 임의로 도입하지 마.**
필요하다고 판단되면 "리스크와 오픈 이슈" 섹션에 **도입 여부 결정 필요**로만 올려.

현재 레포에는 **뷰 레이어(템플릿 엔진, 프론트엔드)와 PDF 라이브러리가 없어.** 이것도 새로 추가하는 의존성이므로:

- 후보를 2~3개 비교하고 추천안을 고르되, 최종 결정은 "오픈 이슈"로 남겨.
- BOM이 관리하는 의존성인지 여부를 표시해. BOM 관리 대상이면 버전을 쓰지 않고, 아니면 `libs.versions.toml`에 선언할 대상으로 표시해.
- 버전은 기억으로 쓰지 말고 `CLAUDE.md`에 적힌 방법(`repo1.maven.org`의 `maven-metadata.xml`)으로 확인해. 확인하지 못했으면 `[확인 필요]`로 표시해.

### 1-3. 외부 기술 조사

- **Notion API**: Context7 MCP로 최신 문서를 확인해. 기억에 의존하지 마.
  - API 버전 헤더, 데이터베이스/데이터 소스 조회 방식
  - 속성 타입별 응답 구조 (title, rich_text, number, date, select, relation, rollup, formula)
  - 인증 방식 (Internal Integration 토큰), rate limit, 페이지네이션
  - 호출에 쓸 HTTP 클라이언트 (Spring 기본 제공 `RestClient` 우선 검토)
- **PDF 생성**: 아래 기준으로 방식을 비교해.
  - 서버에서 HTML → PDF 렌더링 / 브라우저 인쇄(`window.print`) / PDF 라이브러리 직접 생성
  - 비교 기준: 한글 폰트 임베딩, A4 레이아웃 재현도, 표가 여러 페이지로 넘어갈 때 처리, 웹 화면과의 일치도, 서버 부하

## 2단계: 질문 (최대 5개)

PRD 품질에 큰 영향을 주는 핵심 질문을 **최대 5개**만 해. 예시:

- 견적서 상태 워크플로우가 필요한가? (작성중 / 발송 / 승인 등)
- 공유 링크에 만료 기한이 필요한가?
- 부가세 계산 방식 (항목별 vs 합계 기준, 원 단위 절사 규칙)
- 공유 토큰을 Notion 속성에 둘지, 로컬 PostgreSQL에 둘지
- 견적서 1건당 예상 항목 수와 월 발행량

내가 답하지 않거나 "알아서 해"라고 하면 합리적으로 가정하고, 본문에 `[가정]` 태그로 표시한 뒤 진행해.

## 3단계: PRD 작성

### MVP 범위

**포함 (Must)**

- Notion 견적서 DB + 견적 항목 DB 연동 (읽기 전용)
- 추측할 수 없는 고유 토큰 URL로 견적서 웹 조회 (로그인 없음)
- 견적서 PDF 다운로드 (웹 화면과 같은 내용)
- 공급가액 / 부가세 / 합계 계산 규칙
- Notion API 응답 캐싱과 rate limit 대응

**제외 (Won't, 이번 MVP에서는)**

- 운영자용 관리 화면 (Notion 자체가 관리 UI 역할)
- 클라이언트 로그인/회원가입, 전자서명, 결제
- 견적서 수정/승인 같은 Notion 쓰기 기능
- 다국어, 다중 통화

범위 밖 기능이 필요해 보이면 본문에 넣지 말고 "향후 과제" 섹션에만 적어.

### 산출물 구조 (이 순서와 번호를 지켜)

1. **개요** — 문제 정의, 해결 방식, 대상 사용자
2. **목표와 성공 지표** — 측정 가능한 KPI 3개 이하
3. **페르소나** — 운영자(견적 작성자), 클라이언트(견적 수신자)
4. **사용자 스토리** — `As a / I want / So that` + 수용 기준(Given/When/Then)
5. **기능 요구사항** — 표: `ID | 기능 | 설명 | 우선순위(MoSCoW) | 관련 스토리`
6. **Notion 데이터 모델** — DB별 표: `속성명 | Notion 타입 | 필수 여부 | 예시 값 | 매핑될 DTO 필드`
7. **시스템 아키텍처**
   - 구성도 (Mermaid)
   - 요청 흐름: 클라이언트 → Controller → Service → Notion 클라이언트 / 캐시 → Notion API
   - 패키지 구조: `domain/<도메인>/` 아래 레이어 배치, `global/`에 추가할 것
8. **API 명세** — 엔드포인트, 요청/응답 예시(`ApiResponse` 포맷), 관련 `ErrorCode`
9. **화면 명세** — 견적서 조회 화면, 에러 화면(없는 링크 / 만료 링크) 와이어프레임 (ASCII)
10. **PDF 요구사항** — 선택한 생성 방식과 이유, 레이아웃, 폰트, 파일명 규칙
11. **비기능 요구사항** — 보안(토큰 URL 엔트로피, Notion 시크릿 관리), 성능 목표(수치), 캐시 전략(TTL, 무효화), 로깅(`@Slf4j`), 헬스체크(Actuator)
12. **예외 시나리오** — 표: `상황 | 사용자에게 보이는 결과 | ErrorCode | HTTP 상태`
    - 최소 포함: Notion 장애, rate limit 초과, 필수 속성 누락, 항목 0개, 없는 토큰, 만료 토큰
13. **테스트 전략** — 단위 테스트 대상, 통합 테스트 범위, Notion API 목킹 방식
    - Testcontainers 통합 테스트는 Docker가 없으면 SKIPPED 처리된다는 점 명시
14. **향후 과제**
15. **리스크와 오픈 이슈** — 새 의존성 도입 결정, 유보 항목(Security 등) 관련 결정 포함
16. **마일스톤** — 1주 단위 작업 분해, 작업별 완료 기준(검증 명령어 포함: `./gradlew build`, `./gradlew test`)

### 작성 규칙

- 한국어로 작성하고, 기술 용어와 코드 식별자는 원문 그대로 둬.
- 구현 코드는 쓰지 마. 인터페이스 수준의 예시(JSON, 테이블 스키마, 패키지 트리)만 넣어.
- "빠르게", "적절히" 같은 모호한 표현 대신 수치나 조건으로 적어.
- 확인하지 못한 외부 사양은 `[확인 필요]`, 가정한 내용은 `[가정]`으로 표시해.
- 결과는 `docs/PRD.md`에 저장해.

## 4단계: 완료 전 셀프 체크

아래 항목을 모두 확인하고, 통과하지 못한 항목은 고친 다음 저장해.

- [ ] 모든 Must 기능이 사용자 스토리와 수용 기준으로 연결되어 있는가
- [ ] Notion 속성 → DTO → 화면/PDF 필드가 빠짐없이 추적되는가
- [ ] 모든 예외 시나리오에 `ErrorCode`가 정의되어 있는가
- [ ] `CLAUDE.md`의 아키텍처 규칙과 충돌하는 설계가 없는가
- [ ] 유보 항목(Spring Security, QueryDSL 등)을 임의로 도입하지 않았는가
- [ ] 새 의존성에 BOM 관리 여부와 버전 확인 상태가 표시되어 있는가
- [ ] 제외 범위의 기능이 본문에 섞여 들어가지 않았는가
- [ ] 개발자가 추가 질문 없이 첫 번째 마일스톤을 시작할 수 있는가
